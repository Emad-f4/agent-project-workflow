# Agent Project Workflow

یک Workflow ساختاریافته برای وادار کردن Agentهای برنامه‌نویسی هوش مصنوعی به کار در یک ساختار مرحله‌ای، قابل پیش‌بینی و قابل اتکا.

## چرا به سمت چنین چیزی رفتم؟

کار با Agentهای برنامه‌نویسی هوش مصنوعی بسیار سریع شده است، اما همین سرعت می‌تواند به یک مشکل تبدیل شود.

فرض کنید یک ایده خام دارید و به Agent می‌گویید:

> «یک برنامه برای مدیریت عادت‌ها بساز.»

Agent ممکن است بلافاصله شروع به تصمیم‌گیری کند؛ خودش ساختار پروژه را تعیین کند، بعضی Skillها یا Workflowهای موردنیاز را ایجاد کند، وارد پیاده‌سازی شود، درباره معماری تصمیم بگیرد یا چندین مرحله از پروژه را بدون هماهنگی با کاربر پشت سر بگذارد.

در نتیجه ممکن است پروژه خیلی سریع ساخته شود، اما الزاماً:

* ساختاریافته نباشد
* قابل پیش‌بینی نباشد
* با نیاز اصلی کاربر کاملاً هم‌راستا نباشد
* تصمیمات آن قابل ردیابی نباشد
* ادامه دادن پروژه در جلسات بعدی دشوار شود

این مسئله باعث شد به یک سؤال ساده برسم:

> **اگر Agent قبل از شروع کار، یک Workflow مشخص برای اجرای پروژه داشته باشد چه می‌شود؟**

به جای اینکه Agent را فقط ابزاری بدانیم که یک Prompt دریافت می‌کند و کد تولید می‌کند، می‌توان یک لایه ساختاریافته بین **کاربر** و **Agent** قرار داد.

```text
User
  │
  │ ایده / نیازمندی / تصمیمات
  ▼
Agent Project Workflow
  │
  ├── Project Specification
  ├── Project Lifecycle
  ├── Phases
  ├── Plans
  ├── Context
  ├── State
  └── Deliverables
  │
  ▼
AI Coding Agent
  │
  ├── Analyze
  ├── Plan
  ├── Execute
  ├── Verify
  └── Report
  │
  ▼
Project
```

هدف این نیست که Agent را محدود یا کم‌توان کنیم.

هدف این است که توانایی Agent را در یک **ساختار مشخص برای اجرای پروژه** قرار دهیم.

# ایده اصلی

ایده اصلی این پروژه تعریف قوانین، ساختار، چرخه عمر پروژه و مسئولیت‌های Agent در قالب چند فایل Markdown است.

این فایل‌ها مانند یک **قرارداد سطح پروژه (Project-Level Contract)** بین کاربر و Agent عمل می‌کنند.

در حالت عادی ممکن است برای هر پروژه بارها به Agent بگوییم:

> «اول نیازمندی‌ها را تحلیل کن.»

> «هنوز شروع به کدنویسی نکن.»

> «ابتدا معماری را مشخص کنیم.»

> «حالا وارد مرحله بعد شو.»

اما در این رویکرد، این انتظارات بخشی از Workflow پروژه هستند.

در نتیجه Agent به جای اینکه برای هر پروژه Workflow خودش را از ابتدا بسازد، از یک فرآیند تعریف‌شده پیروی می‌کند.

این موضوع باعث می‌شود اجرای پروژه:

* قابل پیش‌بینی‌تر
* ساختاریافته‌تر
* قابل ردیابی‌تر
* منسجم‌تر
* مرحله‌محور
* قابل بررسی‌تر
* قابل ادامه در جلسات مختلف

باشد.

# چه چیزی تغییر می‌کند؟

بدون Workflow مشخص:

```text
Idea
  ↓
Agent interpretation
  ↓
Agent decisions
  ↓
Code
  ↓
More agent decisions
  ↓
More code
```

با Workflow:

```text
Idea
  ↓
Requirements
  ↓
Project Definition
  ↓
Planning
  ↓
Architecture / Design
  ↓
Implementation
  ↓
Testing
  ↓
Review
  ↓
Deployment
```

چرخه دقیق پروژه می‌تواند بر اساس نوع پروژه تغییر کند.

نکته اصلی این است که Agent مجبور نباشد برای هر پروژه، فرآیند توسعه را از صفر برای خودش تعریف کند.

# ساختار پروژه

در حال حاضر این Repository شامل سه فایل اصلی برای تعریف رفتار و Workflow پروژه است:

```text
agent-project-workflow/
│
├── AGENTS.md
├── AGENTS.fa.md
│
├── AGENT_PROJECT_SPEC.md
├── AGENT_PROJECT_SPEC.fa.md
│
├── PROJECT_WORKFLOW.md
├── PROJECT_WORKFLOW.fa.md
│
├── README.md
├── README.fa.md
└── LICENSE
```

هر فایل مسئولیت متفاوتی دارد.

---

## 1. `AGENTS.md`

این فایل **دستورالعمل‌های رفتاری Agent** را تعریف می‌کند.

مشخص می‌کند Agent در هنگام کار روی پروژه چگونه باید عمل کند.

برای مثال می‌تواند موارد زیر را مشخص کند:

* Agent قبل از انجام تغییرات چه کاری انجام دهد
* چگونه نیازمندی‌ها را بررسی کند
* چگونه Plan ایجاد کند
* چه زمانی از کاربر تصمیم بخواهد
* چگونه از Workflow پروژه استفاده کند
* چگونه Context پروژه را حفظ کند
* چگونه نتیجه کار را گزارش کند
* چگونه کار خود را بررسی و Verify کند

به زبان ساده:

> **`AGENTS.md` مشخص می‌کند Agent چگونه باید رفتار کند.**

---

# 2. `AGENT_PROJECT_SPEC.md`

این فایل **Specification پروژه‌ای که قرار است توسط Agent مدیریت شود** را تعریف می‌کند.

در این فایل مفاهیم و ساختارهای اصلی سیستم مشخص می‌شوند.

برای مثال:

* Project State
* Current Phase
* Context
* Plans
* Requirements
* Deliverables
* Decisions
* Phase Transitions
* نقاط نیازمند تأیید کاربر

به زبان ساده:

> **`AGENT_PROJECT_SPEC.md` مشخص می‌کند پروژه Agent-managed از چه اجزایی تشکیل شده است.**

---

# 3. `PROJECT_WORKFLOW.md`

این فایل **چرخه عمر پروژه (Project Lifecycle)** را تعریف می‌کند.

برای مثال Workflow یک پروژه می‌تواند به شکل زیر باشد:

```text
Bootstrap
   ↓
Requirements
   ↓
Architecture
   ↓
Design
   ↓
Implementation
   ↓
Testing
   ↓
Review
   ↓
Deployment
   ↓
Maintenance
```

هر Phase می‌تواند موارد زیر را مشخص کند:

* هدف Phase
* ورودی‌ها
* مسئولیت‌های Agent
* تصمیمات کاربر
* خروجی‌های مورد انتظار
* Artifactهای موردنیاز
* معیار خروج از Phase
* شرایط ورود به Phase بعد

به زبان ساده:

> **`PROJECT_WORKFLOW.md` مشخص می‌کند پروژه چگونه از یک مرحله به مرحله بعد حرکت کند.**

---

# ارتباط بین فایل‌ها

این سه فایل عمداً از یکدیگر جدا شده‌اند.

```text
AGENT_PROJECT_SPEC.md
        │
        │ تعریف مدل پروژه
        ▼
PROJECT_WORKFLOW.md
        │
        │ تعریف چرخه عمر
        ▼
AGENTS.md
        │
        │ نحوه رفتار Agent
        ▼
      AGENT
```

یا به شکل ساده‌تر:

| فایل                    | سؤال اصلی                                     |
| ----------------------- | --------------------------------------------- |
| `AGENT_PROJECT_SPEC.md` | پروژه چه ساختار و مدلی دارد؟                  |
| `PROJECT_WORKFLOW.md`   | پروژه چگونه از یک مرحله به مرحله دیگر می‌رود؟ |
| `AGENTS.md`             | Agent هنگام کار چگونه باید رفتار کند؟         |

این تفکیک باعث می‌شود Workflow، مدل پروژه و دستورالعمل‌های Agent از یکدیگر جدا باشند و بتوانند مستقل‌تر توسعه پیدا کنند.

# نحوه استفاده

استفاده از این Workflow بسیار ساده است.

سه فایل اصلی را در Root پروژه خود قرار دهید:

```text
your-project/
│
├── AGENTS.md
├── AGENT_PROJECT_SPEC.md
├── PROJECT_WORKFLOW.md
│
└── ...
```

سپس به Coding Agent خود بگویید ابتدا این سه فایل را بخواند.

برای مثال:

```text
AGENTS.md، AGENT_PROJECT_SPEC.md و PROJECT_WORKFLOW.md را بخوان.

این فایل‌ها Workflow پروژه و مسئولیت‌های تو به عنوان Coding Agent را تعریف می‌کنند.

در تمام طول پروژه بر اساس این فایل‌ها عمل کن.
```

پس از آن Agent این فایل‌ها را به عنوان دستورالعمل‌های اصلی پروژه در نظر می‌گیرد.

هدف این است که Agent به جای ساختن یک Workflow جداگانه برای پروژه، **در Workflow تعریف‌شده برای پروژه کار کند.**

# از ایده خام تا پروژه ساختاریافته

یکی از مهم‌ترین کاربردهای این سیستم زمانی است که پروژه با یک ایده ناقص یا خام شروع می‌شود.

برای مثال:

```text
«یک برنامه می‌خواهم که به کاربران
برای ایجاد و ترک عادت‌ها کمک کند.»
```

به جای اینکه Agent بلافاصله شروع به کدنویسی کند، Workflow می‌تواند پروژه را مرحله‌به‌مرحله جلو ببرد:

```text
Raw Idea
   ↓
Understanding the Problem
   ↓
Clarifying Requirements
   ↓
Defining the Product
   ↓
Planning
   ↓
Architecture
   ↓
Design
   ↓
Implementation
   ↓
Testing
   ↓
Review
```

در این فرآیند، کاربر در نقاط مهم تصمیم‌گیری می‌کند.

Agent همچنان می‌تواند در تحلیل، تحقیق، برنامه‌ریزی، طراحی، پیاده‌سازی، تست و مستندسازی کمک کند؛ اما این فعالیت‌ها **داخل یک ساختار مشخص** انجام می‌شوند.

# چرا Markdown؟

این Workflow عمداً با Markdown پیاده‌سازی شده است و به یک نرم‌افزار Orchestrator یا سیستم پیچیده وابسته نیست.

مزایا:

* قابل خواندن برای انسان
* قابل خواندن برای Agent
* قابل Version Control
* ساده برای تغییر
* ساده برای Review
* ساده برای Fork
* قابل استفاده با Agentهای مختلف
* بدون نیاز به Runtime یا Dependency خاص

در واقع Workflow نیز مانند کد و مستندات، بخشی از Repository پروژه می‌شود و همراه با پروژه تکامل پیدا می‌کند.

# یک اصل ساده

این پروژه بر اساس یک اصل ساده شکل گرفته است:

> **یک AI Coding Agent نباید فقط بداند چه چیزی باید ساخته شود؛ باید بداند پروژه قرار است چگونه پیش برود.**

یک Agent قدرتمند می‌تواند با سرعت بسیار زیادی کد تولید کند.

اما چالش اصلی فقط تولید کد نیست.

چالش اصلی حفظ موارد زیر است:

* جهت پروژه
* Context
* انسجام
* وضعیت پروژه
* نیازمندی‌ها
* تصمیمات
* مرز بین Phaseها
* کنترل و تصمیم‌گیری انسانی

این Workflow تلاش می‌کند با ایجاد یک ساختار مشخص بین **هدف و تصمیمات کاربر** و **اجرای Agent**، این مسئله را حل کند.
